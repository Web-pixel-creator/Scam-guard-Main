# Requirements Document

> Current implementation note (2026-06-01): this MVP is implemented in `main`.
> Runtime is self-hosted Node/Nitro `node-server`; AI uses the OpenAI-compatible
> env contract (`OPENAI_API_KEY`, optional `OPENAI_MODEL`, `OPENAI_BASE_URL`).
> Older platform names in historical text should be read through this current
> deployment model.

## Introduction

Документ описывает требования к MVP Telegram-бота для проекта **Ishonch Guard** — антимошеннического ассистента для Узбекистана. Бот добавляется как **новый канал** к уже работающему веб-приложению и **переиспользует** существующий risk engine (`src/lib/risk/*`) и серверные функции (`checkInput`, `ocrExtract`, `submitReport`), а также общую модель данных Supabase (таблицы `checks`, `reports`, `entities`).

Цель бота — дать пользователю в Telegram возможность задать один вопрос: «Безопасны ли этот звонок, сообщение, ссылка, бот или платёжный запрос?» — и получить понятный ответ: уровень риска (`safe` / `unknown` / `suspicious` / `high_risk`), короткое объяснение простым языком, перечень обнаруженных «красных флагов» (reason codes), конкретные следующие шаги (ADVICE) и возможность отправить жалобу на мошенника.

Бот должен работать на трёх языках (RU / UZ / EN), учитывать локальные сценарии мошенничества (поддельный Центробанк / банк / оператор, фейковые кредиты, кража OTP, установка APK, перевод на «безопасный счёт», просьба отсканировать QR-код для захвата Telegram-аккаунта, схема «родственник/друг в беде — срочно переведите», затягивание живого звонка) и строго соблюдать приватность: чувствительные данные редактируются и хешируются, изображения не сохраняются, никого нельзя называть мошенником поимённо.

Ключевой архитектурный принцип сохраняется: **scoring выполняется детерминированными правилами (rules-first), AI только объясняет**. Если AI provider недоступен, бот продолжает выдавать уровень риска и советы, теряя лишь текстовое объяснение.

## Glossary

- **Bot (Telegram_Bot)**: серверный компонент Ishonch Guard, принимающий и отвечающий на сообщения через Telegram Bot API.
- **Webhook_Handler**: серверная функция, принимающая HTTP-запросы Telegram при доставке обновлений (updates) боту.
- **Telegram_Update**: единица входящего события от Telegram Bot API (сообщение, команда, нажатие кнопки и т.п.).
- **Telegram_User_Id**: числовой идентификатор пользователя Telegram, отправившего сообщение.
- **Chat_Id**: числовой идентификатор чата Telegram, в котором происходит взаимодействие.
- **Risk_Engine**: существующий модуль `src/lib/risk/*` (`detect.ts`, `rules.ts`, `hash.ts`, `rate-limit.ts`).
- **Check_Pipeline**: существующая логика проверки (`checkInput`): `detectInputType` → `normalize` → `redactText`/`maskForDisplay` → правила `evaluate*` → lookup в `entities` → `scoreFromCodes` → `aiExplain` → запись в `checks`.
- **OCR_Pipeline**: существующая логика `ocrExtract` / `ocrScreenshot` — извлечение и редактирование текста из изображения через OpenAI-compatible vision model.
- **Report_Pipeline**: существующая логика `submitReport` — вставка строки в `reports` и upsert/инкремент строки в `entities`.
- **Risk_Level**: один из `safe | unknown | suspicious | high_risk` (enum `risk_level`).
- **Input_Type**: один из `phone | telegram | url | text | payment | apk | unknown` (enum `input_type`).
- **Reason_Code**: код «красного флага» из `rules.ts` (например `asks_for_otp`, `apk_download_link`).
- **ADVICE**: набор трилингвальных советов по уровню риска из `rules.ts`.
- **REASON_LABELS**: трилингвальные человекочитаемые названия reason codes из `rules.ts`.
- **AI_Provider**: OpenAI-compatible AI provider (`OPENAI_BASE_URL`), модель `OPENAI_MODEL`.
- **OPENAI_API_KEY**: секретный ключ доступа к AI_Provider.
- **Webhook_Secret_Token**: секретный токен, передаваемый Telegram в заголовке `X-Telegram-Bot-Api-Secret-Token` для подтверждения подлинности webhook-запроса.
- **Bot_Token**: секретный токен авторизации бота в Telegram Bot API, хранимый только на сервере.
- **Language (Lang)**: выбранный язык интерфейса бота, один из `ru | uz | en`.
- **Session_State**: серверно хранимое состояние диалога конкретного `Telegram_User_Id` (выбранный язык, текущий шаг сценария).
- **Confirmed_Entity**: строка таблицы `entities` со значением `moderation_status='confirmed'`.
- **Sensitive_Data**: OTP/SMS-коды, полные номера карт, PIN, CVV/CVC, пароли, паспортные данные.

## Requirements

### Requirement 1: Запуск бота и приветствие (`/start`)

**User Story:** Как новый пользователь Telegram, я хочу запустить бота командой `/start`, чтобы понять, что бот делает, и выбрать язык общения.

#### Acceptance Criteria

1. WHEN пользователь отправляет команду `/start`, THE Telegram_Bot SHALL отправить приветственное сообщение с кратким описанием возможностей и кнопками выбора языка (`Русский`, `O‘zbekcha`, `English`).
2. WHEN пользователь выбирает язык, THE Telegram_Bot SHALL сохранить выбранный Language в Session_State для соответствующего Telegram_User_Id.
3. WHEN пользователь выбрал язык, THE Telegram_Bot SHALL отправить инструкцию о том, какие данные можно прислать (номер телефона, Telegram-username, ссылку, APK-ссылку, текст сообщения, скриншот, описание ситуации) на выбранном Language.
4. IF у Telegram_User_Id отсутствует сохранённый Language в Session_State, THEN THE Telegram_Bot SHALL принудительно отображать содержимое на Language `ru` по умолчанию.
5. THE Telegram_Bot SHALL отображать все элементы приветствия (текст, подписи кнопок) на выбранном Language.

### Requirement 2: Выбор и переключение языка (RU/UZ/EN)

**User Story:** Как пользователь, я хочу выбрать или сменить язык в любой момент, чтобы получать ответы на понятном мне языке.

#### Acceptance Criteria

1. WHEN пользователь отправляет команду выбора языка (например `/lang`), THE Telegram_Bot SHALL отобразить кнопки выбора языка (`ru`, `uz`, `en`).
2. WHEN пользователь выбирает новый Language, THE Telegram_Bot SHALL обновить Language в Session_State и подтвердить смену на выбранном Language.
3. IF обновление Language в Session_State завершается ошибкой, THEN THE Telegram_Bot SHALL ответить пользователю на ранее использовавшемся Language (или `ru` по умолчанию) и залогировать ошибку без раскрытия Sensitive_Data.
4. THE Telegram_Bot SHALL формировать тексты объяснений, REASON_LABELS и ADVICE на текущем Language из Session_State.
5. WHERE запрашиваемый Language равен `uz`, THE Telegram_Bot SHALL использовать узбекский (латиница) вариант строк.

### Requirement 3: Справка и безопасность (`/help`, `/safety`)

**User Story:** Как пользователь, я хочу получить справку по командам и базовые правила безопасности, чтобы понимать, как пользоваться ботом и как не стать жертвой.

#### Acceptance Criteria

1. WHEN пользователь отправляет команду `/help`, THE Telegram_Bot SHALL отправить список доступных команд (`/start`, `/check`, `/report`, `/emergency`, `/help`, `/safety`, `/lang`) с кратким описанием каждой на текущем Language.
2. WHEN пользователь отправляет команду `/safety`, THE Telegram_Bot SHALL отправить набор базовых правил безопасности на текущем Language, включающих как минимум: не сообщать OTP/SMS-код/PIN/CVV/пароль, не устанавливать APK по ссылке, перезванивать в банк по официальному номеру.
3. THE Telegram_Bot SHALL включать в ответ `/safety` напоминание о том, что бот анализирует только то содержимое, которое пользователь явно прислал.

### Requirement 4: Проверка содержимого через единый Check_Pipeline (`/check`)

**User Story:** Как пользователь, я хочу прислать номер, username, ссылку, APK-ссылку или текст и получить оценку риска, чтобы понять, безопасно ли это.

#### Acceptance Criteria

1. WHEN пользователь отправляет команду `/check`, THE Telegram_Bot SHALL запросить у пользователя содержимое для проверки на текущем Language.
2. WHEN пользователь присылает текстовое содержимое для проверки, THE Telegram_Bot SHALL передать содержимое и текущий Language в Check_Pipeline без изменения существующей логики scoring.
3. THE Telegram_Bot SHALL определять Input_Type через существующую функцию `detectInputType`, не реализуя собственное определение типа.
4. WHEN Check_Pipeline возвращает результат, THE Telegram_Bot SHALL отправить пользователю Risk_Level, краткое объяснение, список обнаруженных Reason_Code (через REASON_LABELS) и советы (ADVICE) на текущем Language.
5. WHEN Risk_Level равен `high_risk` или `suspicious`, THE Telegram_Bot SHALL отобразить визуальный индикатор уровня (например эмодзи/метку), соответствующий уровню риска.
6. WHEN результат проверки сформирован, THE Telegram_Bot SHALL приложить inline-кнопки «Сообщить» (Report) и «Проверить ещё» (Check another) на текущем Language.
7. WHEN пользователь присылает содержимое в бот без предварительной команды `/check`, THE Telegram_Bot SHALL обработать это содержимое как запрос на проверку через Check_Pipeline.
8. WHEN пользователь присылает содержимое сразу после команды `/check` (отдельным сообщением), THE Telegram_Bot SHALL передать это содержимое напрямую в Check_Pipeline.
9. WHEN пользователь отправляет команду `/check` и содержимое в одном сообщении одновременно, THE Telegram_Bot SHALL обработать это как command-initiated проверку по явному `/check`-сценарию.
10. IF присланный текст превышает максимальную длину, поддерживаемую Check_Pipeline (2000 символов), THEN THE Telegram_Bot SHALL обрезать или отклонить ввод с понятным сообщением на текущем Language вместо передачи невалидного запроса.
11. WHERE результат содержит данные о подтверждённых жалобах (`knownReports` > 0 для Confirmed_Entity), THE Telegram_Bot SHALL сообщить количество подтверждённых жалоб на текущем Language.

### Requirement 5: Проверка скриншотов через OCR_Pipeline без сохранения изображений

**User Story:** Как пользователь, я хочу прислать скриншот переписки или сообщения, чтобы бот распознал текст и оценил риск, не сохраняя моё изображение.

#### Acceptance Criteria

1. WHEN пользователь присылает изображение (фото или документ-изображение), THE Telegram_Bot SHALL извлечь и отредактировать текст через OCR_Pipeline (OpenAI-compatible vision model) на текущем Language.
2. THE Telegram_Bot SHALL передавать извлечённый отредактированный текст в Check_Pipeline для оценки риска.
3. THE Telegram_Bot SHALL обрабатывать изображение только в памяти на время запроса и не сохранять файл изображения в базу данных, объектное хранилище или на диск.
4. WHEN обработка изображения завершена, THE Telegram_Bot SHALL отправить тот же формат результата, что и для текстовой проверки (Risk_Level, объяснение, Reason_Code, ADVICE, кнопки Report / Check another).
5. IF размер изображения превышает лимит OCR_Pipeline (6 МБ), THEN THE Telegram_Bot SHALL отклонить изображение с понятным сообщением на текущем Language.
6. IF OCR_Pipeline не возвращает текст (например AI_Provider недоступен), THEN THE Telegram_Bot SHALL сообщить пользователю, что распознать текст не удалось, и предложить прислать содержимое текстом.

### Requirement 6: Отправка жалобы через Report_Pipeline (`/report`)

**User Story:** Как пользователь, я хочу пожаловаться на мошенника, указав значение, описание и при желании тип мошенничества/город/сумму, чтобы пополнить общую базу через тот же конвейер модерации.

#### Acceptance Criteria

1. WHEN пользователь отправляет команду `/report` или нажимает кнопку «Сообщить», THE Telegram_Bot SHALL запросить значение для жалобы (номер, username, ссылка и т.п.) на текущем Language.
2. WHEN пользователь предоставил значение, THE Telegram_Bot SHALL запросить описание ситуации на текущем Language.
3. THE Telegram_Bot SHALL запрашивать опциональные поля (тип мошенничества, город, сумма ущерба в UZS) как необязательные шаги, которые пользователь может пропустить.
4. WHEN пользователь завершил ввод жалобы, THE Telegram_Bot SHALL передать значение, описание, опциональные поля и текущий Language в Report_Pipeline (`submitReport`) без обхода существующей логики upsert в `entities`.
5. IF длина описания меньше 5 или больше 5000 символов, THEN THE Telegram_Bot SHALL отклонить ввод с понятным сообщением и запросить корректное описание на текущем Language.
6. IF длина значения превышает 500 символов, THEN THE Telegram_Bot SHALL отклонить значение с понятным сообщением на текущем Language.
7. WHEN Report_Pipeline возвращает успех, THE Telegram_Bot SHALL подтвердить приём жалобы и сообщить, что запись станет публичной только после модерации, на текущем Language.
8. IF Report_Pipeline возвращает ошибку, THEN THE Telegram_Bot SHALL сообщить пользователю о неудаче и предложить повторить попытку позже на текущем Language.

### Requirement 7: Приватность и редактирование чувствительных данных

**User Story:** Как пользователь, я хочу быть уверенным, что мои коды, номера карт и личные данные не сохраняются в открытом виде, чтобы безопасно пользоваться ботом.

#### Acceptance Criteria

1. THE Telegram_Bot SHALL редактировать Sensitive_Data через существующий `redactText` до любой записи в базу данных.
2. THE Telegram_Bot SHALL хешировать идентификаторы (номер, username, URL) через существующий `hashIdentifier` перед записью в `checks`, `reports` или `entities`.
3. THE Telegram_Bot SHALL сохранять для отображения только маскированные строки (`maskForDisplay` / `redacted_value`), а не исходные идентификаторы.
4. THE Telegram_Bot SHALL передавать в любую запись только те данные, которые уже проходят редактирование и хеширование в Check_Pipeline и Report_Pipeline.
5. THE Telegram_Bot SHALL формировать объяснения и сообщения так, чтобы они не содержали полные значения Sensitive_Data.

### Requirement 8: Запрет на обвинение конкретного лица

**User Story:** Как продукт, я хочу, чтобы бот сообщал только об уровне риска, а не обвинял конкретного человека, чтобы избежать доксинга и ложных обвинений.

#### Acceptance Criteria

1. THE Telegram_Bot SHALL описывать результат только через Risk_Level и Reason_Code, без формулировок, утверждающих, что конкретное названное лицо является мошенником.
2. THE Telegram_Bot SHALL включать в системную инструкцию для AI_Provider требование не обвинять конкретное лицо (сохраняя существующее поведение `aiExplain`).
3. WHERE результат относится к Confirmed_Entity, THE Telegram_Bot SHALL сообщать только агрегированные данные (уровень риска, количество подтверждённых жалоб), без раскрытия личности.

### Requirement 9: Публичность жалоб только после модерации

**User Story:** Как продукт, я хочу, чтобы жалобы появлялись публично только после проверки администратором, чтобы предотвратить массовые ложные доносы.

#### Acceptance Criteria

1. WHEN жалоба создаётся через бот, THE Report_Pipeline SHALL создавать или обновлять строку `entities` с `moderation_status='new'`.
2. THE Telegram_Bot SHALL отображать в результатах проверки данные о жалобах только для Confirmed_Entity (`moderation_status='confirmed'`).
3. THE Telegram_Bot SHALL не реализовывать собственный путь записи в `entities`, минующий конвейер модерации.

### Requirement 10: Ограничение частоты запросов по пользователю Telegram

**User Story:** Как оператор сервиса, я хочу ограничивать частоту запросов от одного пользователя Telegram, чтобы защититься от спама и злоупотреблений.

#### Acceptance Criteria

1. WHEN пользователь отправляет запрос на проверку или жалобу, THE Telegram_Bot SHALL применять rate limit по ключу, основанному на Telegram_User_Id (или Chat_Id), аналогичный веб-лимиту 10 запросов в минуту.
2. IF пользователь превышает лимит запросов, THEN THE Telegram_Bot SHALL отправить сообщение о превышении лимита с указанием времени повторной попытки (retryAfter) на текущем Language.
3. THE Telegram_Bot SHALL использовать ключ rate limit, основанный на Telegram_User_Id, а не на IP-адресе, поскольку запросы поступают от сервера Telegram.
4. THE Telegram_Bot SHALL обрабатывать in-memory ограничитель как best-effort защиту (per-worker), не полагаясь на него как на жёсткую глобальную гарантию.

### Requirement 11: Анализ только явно присланного содержимого

**User Story:** Как пользователь, я хочу контролировать, что именно анализирует бот, чтобы он не сканировал мои приватные чаты автоматически.

#### Acceptance Criteria

1. THE Telegram_Bot SHALL анализировать только то содержимое, которое пользователь явно отправил или переслал боту в личном чате с ботом.
2. THE Telegram_Bot SHALL не анализировать содержимое, поступающее иными путями, кроме явной отправки/пересылки пользователем в личном чате.
3. IF анализ явно присланного содержимого завершается ошибкой, THEN THE Telegram_Bot SHALL обработать сбой через повтор (retry) или уведомление пользователя, не оставляя запрос без ответа.
4. THE Telegram_Bot SHALL не запрашивать и не использовать доступ к содержимому других чатов пользователя.
5. WHEN пользователь пересылает (forward) сообщение боту, THE Telegram_Bot SHALL обрабатывать текст пересланного сообщения как обычный ввод для Check_Pipeline.

### Requirement 12: Безопасная обработка Telegram webhook

**User Story:** Как оператор сервиса, я хочу, чтобы webhook принимал только подлинные запросы от Telegram, чтобы защититься от поддельных обновлений.

#### Acceptance Criteria

1. WHEN Webhook_Handler получает HTTP-запрос, THE Webhook_Handler SHALL сначала проверять совпадение заголовка `X-Telegram-Bot-Api-Secret-Token` с настроенным Webhook_Secret_Token до любой валидации структуры запроса.
2. IF заголовок Webhook_Secret_Token отсутствует или не совпадает, THEN THE Webhook_Handler SHALL отклонить запрос с HTTP-статусом 401, не выполнять валидацию структуры Telegram_Update и не обрабатывать его.
3. WHEN проверка Webhook_Secret_Token проходит успешно, THE Webhook_Handler SHALL валидировать структуру входящего Telegram_Update и игнорировать неподдерживаемые типы обновлений.
4. WHEN Webhook_Handler принимает валидный Telegram_Update, THE Webhook_Handler SHALL ответить Telegram HTTP-статусом 200 после постановки обработки в работу.
5. IF обработка Telegram_Update вызывает внутреннюю ошибку (processing error) после успешной проверки токена, THEN THE Webhook_Handler SHALL логировать ошибку и возвращать Telegram HTTP-статус 200, чтобы избежать бесконечных повторных доставок.
6. IF ошибка возникает на этапе проверки токена (token validation error), THEN THE Webhook_Handler SHALL возвращать HTTP-статус 401, а не 200.

### Requirement 13: Деградация при недоступности AI_Provider

**User Story:** Как пользователь, я хочу получать уровень риска и советы даже если AI-объяснение недоступно, чтобы сервис оставался полезным при сбоях.

#### Acceptance Criteria

1. IF OPENAI_API_KEY отсутствует или AI_Provider возвращает ошибку, THEN THE Telegram_Bot SHALL всё равно отправить Risk_Level, список Reason_Code и ADVICE на текущем Language.
2. THE Telegram_Bot SHALL всегда отправлять советы (ADVICE) даже при полном отсутствии доступа к AI_Provider, используя локальный ADVICE из `rules.ts` как fallback-контент.
3. WHEN AI-объяснение недоступно (`explanation` = null), THE Telegram_Bot SHALL отправить результат без блока текстового объяснения, не показывая пользователю техническую ошибку, связанную с AI.
4. WHERE сбой относится не к AI (например сетевые ошибки Telegram API, ошибки валидации ввода), THE Telegram_Bot SHALL обрабатывать и при необходимости показывать такие ошибки независимо от недоступности AI-объяснения.
5. THE Telegram_Bot SHALL вычислять Risk_Level и score исключительно через детерминированные правила `scoreFromCodes`, независимо от доступности AI_Provider.

### Requirement 14: Локальные сценарии мошенничества Узбекистана

**User Story:** Как местный пользователь, я хочу, чтобы бот распознавал типичные узбекистанские схемы мошенничества, чтобы предупреждения были релевантными.

#### Acceptance Criteria

1. THE Telegram_Bot SHALL использовать существующие правила `evaluateText/evaluateUrl/evaluatePhone/evaluateTelegram`, покрывающие сценарии поддельного Центробанка/банка/оператора, фейковых кредитов, кражи OTP/SMS-кода, установки APK и перевода на «безопасный счёт».
2. WHEN обнаружен Reason_Code, связанный с локальным сценарием (например `impersonates_bank`, `asks_for_otp`, `apk_download_link`, `asks_to_transfer_to_safe_account`), THE Telegram_Bot SHALL отобразить соответствующую метку REASON_LABELS на текущем Language.
3. THE Telegram_Bot SHALL поддерживать ввод на русском и узбекском (латиница), как это поддерживают существующие правила.
4. WHEN присланное содержимое содержит просьбу отсканировать QR-код (например для «входа», «подтверждения», «верификации»), THE Telegram_Bot SHALL классифицировать это как высокий риск через Reason_Code `asks_to_scan_qr` и предупредить, что сканирование чужого QR может дать мошеннику доступ к Telegram-аккаунту.
5. WHEN присланное содержимое описывает срочный перевод денег из-за беды с родственником или другом (например «друг попал в аварию, срочно нужны деньги на лечение»), THE Telegram_Bot SHALL отметить это через Reason_Code `relative_in_distress` и посоветовать связаться с этим человеком напрямую по известному номеру перед любым переводом.
6. WHEN присланное содержимое содержит просьбу назвать или подтвердить части данных карты (например «подтвердите последние 4 цифры карты»), THE Telegram_Bot SHALL отметить это через Reason_Code `requests_card_digits` и предупредить, что банк не запрашивает цифры карты, коды или их части.
7. WHEN присланное содержимое угрожает блокировкой счёта/карты при бездействии (например «карта будет заблокирована через 24 часа, подтвердите сейчас»), THE Telegram_Bot SHALL отметить это через Reason_Code `threatens_account_block` в сочетании с `uses_urgency`.
8. WHERE сценарий относится к давлению на живом звонке (затягивание разговора, «не кладите трубку») или к звонку голосом, который «звучит как банк или близкий», THE Telegram_Bot SHALL выдавать поведенческую рекомендацию положить трубку и самостоятельно перезвонить в организацию/человеку по известному официальному номеру, не полагаясь на детекцию длительности звонка или анализ аудио.

### Requirement 15: Управление состоянием диалога

**User Story:** Как пользователь, я хочу проходить многошаговые сценарии (выбор языка, отправка жалобы) без потери контекста, чтобы взаимодействие было предсказуемым.

#### Acceptance Criteria

1. THE Telegram_Bot SHALL хранить Session_State по Telegram_User_Id, включая выбранный Language и текущий шаг активного сценария.
2. WHEN любой многошаговый сценарий начинается, THE Telegram_Bot SHALL немедленно сохранить Session_State (с текущим шагом сценария) ещё до получения первого ответа пользователя.
3. WHEN пользователь находится в многошаговом сценарии (например ввод жалобы) и присылает следующее сообщение, THE Telegram_Bot SHALL интерпретировать сообщение как ответ на текущий шаг.
4. WHEN пользователь отправляет команду (начинающуюся с `/`) во время активного сценария, THE Telegram_Bot SHALL прервать текущий сценарий и начать обработку новой команды.
5. WHEN многошаговый сценарий завершён, THE Telegram_Bot SHALL сбросить шаг сценария в Session_State в нейтральное состояние.

### Requirement 16: Обработка неподдерживаемого и пустого ввода

**User Story:** Как пользователь, я хочу получать понятную подсказку при отправке неподдерживаемого содержимого, чтобы знать, что делать дальше.

#### Acceptance Criteria

1. IF пользователь присылает пустое сообщение или содержимое, которое не удаётся обработать (например стикер, голосовое/аудио, видео, геолокацию), THEN THE Telegram_Bot SHALL отправить подсказку о поддерживаемых типах ввода на текущем Language.
2. IF пользователь отправляет неизвестную команду, THEN THE Telegram_Bot SHALL предложить воспользоваться `/help` на текущем Language.
3. WHEN пользователь присылает несколько изображений в одном сообщении, THE Telegram_Bot SHALL обработать одно изображение и сообщить, что обрабатывается только одно изображение за раз, на текущем Language.

### Requirement 17: Bot_Token и секреты только на сервере

**User Story:** Как оператор сервиса, я хочу, чтобы токен бота и другие секреты хранились только на сервере, чтобы исключить их утечку в клиентский код или репозиторий.

#### Acceptance Criteria

1. THE Telegram_Bot SHALL читать Bot_Token, Webhook_Secret_Token и OPENAI_API_KEY только из серверных переменных окружения.
2. THE Telegram_Bot SHALL обращаться к Telegram Bot API и AI_Provider исключительно из серверного кода (server function / edge handler), не из клиентского bundle.
3. THE Telegram_Bot SHALL выполнять записи в `checks`, `reports` и `entities` через серверный клиент с service-role ключом (`supabaseAdmin`), как это делают существующие серверные функции.
4. IF Bot_Token или Webhook_Secret_Token не сконфигурированы, THEN THE Webhook_Handler SHALL отклонять обработку обновлений и логировать ошибку конфигурации без раскрытия значений секретов.

### Requirement 18: Время ответа и производительность

**User Story:** Как пользователь, я хочу получать ответ за несколько секунд, чтобы бот был удобен в реальной ситуации.

#### Acceptance Criteria

1. WHEN пользователь присылает текстовый ввод для проверки и AI_Provider доступен, THE Telegram_Bot SHALL отправить результат в течение 10 секунд при штатной работе зависимостей.
2. WHILE Check_Pipeline или OCR_Pipeline выполняется дольше 3 секунд, THE Telegram_Bot SHALL отправить промежуточный индикатор обработки (например действие «typing» или сообщение «Анализирую…») на текущем Language.
3. WHEN AI_Provider недоступен, THE Telegram_Bot SHALL отправить результат на основе детерминированных правил без ожидания таймаута AI сверх настроенного предела.

### Requirement 19: Наблюдаемость и логирование без утечки данных

**User Story:** Как оператор сервиса, я хочу видеть логи работы бота для диагностики, не раскрывая чувствительные данные пользователей.

#### Acceptance Criteria

1. WHEN обрабатывается Telegram_Update, THE Telegram_Bot SHALL логировать тип события, Input_Type и Risk_Level без записи в лог исходного содержимого пользователя или Sensitive_Data.
2. IF при обработке возникает ошибка, THEN THE Telegram_Bot SHALL логировать сообщение об ошибке и контекст без полных идентификаторов и Sensitive_Data.
3. THE Telegram_Bot SHALL не записывать в логи Bot_Token, Webhook_Secret_Token, OPENAI_API_KEY или полные значения присланных идентификаторов.

### Requirement 20: Режим паники и экстренные шаги (`/emergency`)

**User Story:** Как пользователь, который уже отправил код или перевёл деньги (или находится под давлением на звонке), я хочу получить чёткий список срочных действий, чтобы минимизировать ущерб в первые часы.

#### Acceptance Criteria

1. WHEN пользователь отправляет команду `/emergency` или нажимает кнопку «Я уже отправил код/деньги», THE Telegram_Bot SHALL отправить пронумерованный чек-лист экстренных действий на текущем Language.
2. THE Telegram_Bot SHALL включать в чек-лист как минимум: положить трубку и не продолжать разговор; срочно позвонить в банк по официальному номеру и заблокировать карту/онлайн-банк; сменить пароль Telegram и завершить активные сессии; не сканировать чужие QR-коды; сохранить скриншоты как доказательства; подать заявление (Cyber Police 102).
3. WHERE результат проверки равен `high_risk`, THE Telegram_Bot SHALL приложить inline-кнопку быстрого доступа к экстренным шагам в дополнение к стандартным кнопкам результата.
4. THE Telegram_Bot SHALL предоставлять чек-лист экстренных шагов без запроса Sensitive_Data у пользователя.
5. WHEN пользователь описывает давление на живом звонке (затягивание, «не кладите трубку»), THE Telegram_Bot SHALL включать в ответ поведенческий скрипт: завершить звонок и самостоятельно перезвонить в организацию по известному официальному номеру.

### Requirement 21: Проверка через пересылку контакта (Telegram contact card)

**User Story:** Как пользователь (в том числе пожилой), я хочу просто переслать боту карточку контакта подозрительного абонента, чтобы проверить номер без ручного копирования.

#### Acceptance Criteria

1. WHEN пользователь присылает Telegram contact card (объект `contact` с номером телефона), THE Telegram_Bot SHALL извлечь номер телефона из карточки и передать его в Check_Pipeline как ввод типа `phone`.
2. THE Telegram_Bot SHALL нормализовать, маскировать и хешировать номер из контакта через существующие `normalize`/`maskForDisplay`/`hashIdentifier` так же, как текстовый ввод номера.
3. THE Telegram_Bot SHALL не сохранять имя контакта или иные поля карточки помимо того, что требуется Check_Pipeline, и применять те же правила приватности (редактирование/хеширование).
4. IF contact card не содержит номера телефона, THEN THE Telegram_Bot SHALL сообщить, что номер не найден, и предложить прислать номер текстом на текущем Language.

### Requirement 22: Явные границы объёма MVP

**User Story:** Как владелец продукта, я хочу зафиксировать, что находится вне объёма MVP-бота, чтобы не давать пользователям ложных ожиданий и не расширять скоуп неконтролируемо.

#### Acceptance Criteria

1. THE Telegram_Bot SHALL NOT анализировать содержимое голосовых сообщений, аудио или видео в рамках MVP (распознавание речи и детекция клонированного голоса вне объёма).
2. THE Telegram_Bot SHALL NOT перехватывать или автоматически сканировать звонки, SMS или приватные чаты пользователя; анализируется только явно присланное содержимое (см. Requirement 11).
3. WHEN пользователь присылает тип содержимого вне объёма MVP (голос/аудио/видео), THE Telegram_Bot SHALL вежливо сообщить об ограничении и предложить прислать текст или скриншот на текущем Language.
4. THE Telegram_Bot SHALL формулировать результаты как оценку риска, не как гарантию: ответ `safe`/`unknown` не является разрешением сообщать коды или переводить деньги, и это должно отражаться в формулировках советов.
5. THE Telegram_Bot SHALL рассматривать рассылки/алерты о новых схемах, голосовой ввод, доверенный контакт (family-share) и автоматическую блокировку как функциональность вне MVP, фиксируемую в отдельных спеках.

## Open Product Decisions

Следующие решения не зафиксированы в требованиях и должны быть приняты на этапе design:

1. **Bot framework / runtime** — использовать ли легковесную обработку Telegram Bot API вручную в server function (TanStack Start, как существующие RPC) или библиотеку (`grammY` / `telegraf`). Влияет на структуру Webhook_Handler.
2. **Хостинг webhook-обработчика** — отдельный маршрут в текущем приложении (Node runtime/Nitro node-server preset) против отдельной serverless-функции. Требование 12 предполагает HTTP-эндпоинт, но размещение открыто.
3. **Персистентность Session_State и Language** — in-memory (per-worker, теряется при рестарте, как текущий rate-limit) против таблицы Supabase (новая таблица `telegram_sessions`) против Telegram-side хранения. Влияет на требования 2, 6, 15 и на сохранение языка между сессиями.
4. **Rate-limit store** — переиспользовать существующий in-memory `checkRateLimit` (best-effort, per-worker) против общего хранилища (KV/Redis). Связано с известным риском в `OPEN_TASKS.md`.
5. **Расширение `checks` для канала** — нужно ли добавлять признак канала (web / telegram) в таблицу `checks` для аналитики; сейчас схема его не содержит.
6. **Surface scam alerts (опционально)** — стоит ли в MVP добавлять команду/уведомления о подтверждённых сущностях; в текущих требованиях это вне основного объёма.
